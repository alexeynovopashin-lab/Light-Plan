## 1. Что приложение просит у Open-Meteo (из кода)

Файл `LightPlanData/Weather/WeatherSource.swift`, структура `OpenMeteoSource`.
Сеть — `URLSession.shared.data(from:)`: таймаут системный по умолчанию (60 с на запрос),
заголовков и ключа нет.

### 1.1 Прогноз по часам

`GET https://api.open-meteo.com/v1/forecast`

| параметр | значение |
|---|---|
| `latitude`, `longitude` | `String(Double)` — полные знаки, не округлены |
| `hourly` | `cloud_cover,cloud_cover_low,cloud_cover_mid,cloud_cover_high,relative_humidity_2m,temperature_2m,wind_speed_10m,wind_direction_10m,wind_gusts_10m,precipitation,weather_code` (11 переменных) |
| `forecast_days` | `16` |
| `past_days` | `5` |
| `timezone` | `auto` |
| `windspeed_unit` | `ms` |

Ответ, как его читает `OpenMeteoHourlyResponse`: объект с ключом `hourly`; внутри
массивы одинаковой длины: `time` (строки `2026-09-27T00:00`, местное время точки),
`cloud_cover`, `temperature_2m`, `wind_speed_10m`, `precipitation`, `weather_code`
(обязательны); `cloud_cover_low/mid/high`, `relative_humidity_2m`,
`wind_direction_10m`, `wind_gusts_10m` — необязательны (`[Double]?`).
Остальные ключи ответа (`utc_offset_seconds`, `timezone`, `elevation`, `hourly_units`)
приложение не читает.

**Мерено:** 504 часа (21 сутки × 24), `2026-09-27T00:00` … `2026-10-17T23:00`,
30 334 байта без сжатия, 6 826 байт с gzip, 0,49 с (Mac → Open-Meteo),
`generationtime_ms` ≈ 30.

### 1.2 Воздух

`GET https://air-quality-api.open-meteo.com/v1/air-quality`

| параметр | значение |
|---|---|
| `latitude`, `longitude` | как выше |
| `hourly` | `aerosol_optical_depth,dust` |
| `forecast_days` | `5` |
| `timezone` | `auto` |

Ответ: `hourly.time` + `aerosol_optical_depth`, `dust` — `[Double?]?`; часы без данных
приходят `null` (замер 23.09: 4 из 120; в замере 02.10 — 0 пустых для `dust`).
**Мерено:** 120 часов, 3 672 байта, 0,60 с.

### 1.3 Как приложение зовёт и кэширует (из кода)

- `WeatherStore.scheduleRefresh` — запрос после паузы 500 мс от последней смены
  места; сперва прогноз (`refreshHourly`), потом воздух (`refreshAir`) — **два
  запроса подряд на одну смену места**.
- `WeatherFetcher` — актор, кэш в памяти процесса: ключ `"%.3f,%.3f"` (~100 м),
  **без срока годности**: пока приложение не закрыто, то же место второй раз в
  сеть не идёт. Сбой не кэшируется.
- Сбой любого запроса — `catch { return }`: молча, `isLive` остаётся `false`, повтора
  нет. Это и есть «навсегда выдумка». Воздух без прогноза не спрашивается вовсе.
- `PointWeather` (точки съёмки в карточке, итерация 26) — тот же `WeatherSource`,
  **запрос на точку**, не больше семи точек. Прогноз для точки идёт через
  `fetchHourly` с теми же 16+5 сутками (из кода).
- Веб (`index.html`) ходит по тем же двум адресам; для точек карточки — одним
  запросом со списком координат и `start_date/end_date`. Прокси веб не затрагивает
  (веб заморожен, PWA в рамки 28ж не входит).
- Один `OpenMeteoSource()` создаётся в `AppModel.live` (`AppModel.swift:414`).

## 2. Устройство прокси

### 2.1 Рантайм и точка входа

- **Cloud Function**, рантайм Node.js — как у уже живой `tomsonadmin`
  (`tomson_site:cloud/admin/index.js`, файл без зависимостей). Версию рантайма
  выбрать из списка консоли на момент создания — из доки, не мерено. Нужен только
  встроенный `fetch`/`https`, пакеты не нужны.
- **Точка входа — прямая ссылка на функцию** (`https://functions.yandexcloud.net/<id>`,
  функция «публичная»), без API Gateway. Причина — цена: шлюз 142,3 ₽ за 1 млн
  запросов сверх 100 тыс. бесплатных, функция — 18,97 ₽ за 1 млн сверх 1 млн
  бесплатных (§ 4). Шлюз нужен, только если захочется свой домен, готовый
  CORS или проверка JWT; приложению он не нужен.
- Свой домен (`weather.<домен>`) — позже, когда у Алексея будет домен
  (домены Light Plan сегодня не заведены; из `INDEX.md`). В настройках сборки адрес
  меняется одной строкой (§ 7).

### 2.2 Запрос от приложения

Один адрес, два вида запроса — зеркало двух запросов Open-Meteo, чтобы ответ был
**байт в байт ответом Open-Meteo**:

```
GET <base>/forecast?lat=56.488&lon=84.947          → ответ /v1/forecast (§ 1.1)
GET <base>/air?lat=56.488&lon=84.947               → ответ /v1/air-quality (§ 1.2)
```

Параметры `hourly`, `forecast_days`, `past_days`, `timezone`, `windspeed_unit` из
приложения **не передаются** — они зашиты в функции. Так чужой клиент не может
заказать через нас что угодно (экономит лимит Open-Meteo и закрывает дыру
«прокси на весь интернет»). Цена: поменять набор переменных = выложить функцию заново
(приложение при этом то же). Заголовок `X-LP-Key` — § 3.

### 2.3 Пересылка и кэш

1. Проверка: `lat` ∈ [−90, 90], `lon` ∈ [−180, 180], оба числа, иначе `400`.
2. Округление точки до **двух знаков** (~1 км). Основание: у Open-Meteo сетка моделей
   километры и больше (из доки Open-Meteo, не мерено), три знака приложения дают ту
   же ячейку — «лишние» запросы к Open-Meteo без выигрыша в точности. Высотная
   поправка температуры по ячейке на таком шаге различается мало (не мерено —
   проверить в шаге 2: два соседних значения по 0,005° дают ли разный `temperature_2m`).
3. Ключ кэша: `<вид>|<lat2>,<lon2>|<UTC-дата>|<час-окно>`. Дата нужна потому, что окно
   `past_days/forecast_days` сдвигается с началом суток; час-окно — чтобы ответ не
   жил дольше срока.
4. Срок: прогноз — **1 час**, воздух — **3 часа**. Основание — частота обновления
   моделей у Open-Meteo (из доки, не мерено); цифры — предложение, меняются
   константой. Уточнение к шагу 2: заголовки/поле ответа с временем модели.
5. **Где живёт кэш.** Сама функция состояния между вызовами не гарантирует (память
   живого экземпляра — бонус, не опора). Варианты:
   - (а) только память экземпляра + `Cache-Control: max-age=…` на ответе — ноль
     денег и ноль новых сервисов, но при холодных экземплярах кэш пустеет;
   - (б) **приватный бакет** (отдельный от `lightplan`, тот открыт на чтение всем)
     объект на ключ — копейки за хранение и запросы, кэш общий для всех экземпляров;
   - (в) YDB serverless — лишняя сущность, для 2 ключей на точку не нужна.
   Предложение: (а) для первой выкладки, (б) — если замер шага 2 покажет, что
   холодные экземпляры дают заметную долю обращений в Open-Meteo.
6. Запрос в Open-Meteo — с таймаутом (предложение: 8 с), один повтор.

### 2.4 Ответы при ошибке

| ситуация | код | тело | что делает приложение |
|---|---|---|---|
| нет/неверный ключ, не тот метод | `403` | `{"error":true,"reason":"…"}` | как сбой: выдумка + повтор (§ 7) |
| неверные координаты | `400` | как у Open-Meteo | сбой |
| Open-Meteo отдал `429`/`5xx`/таймаут, но в кэше есть **просроченный** ответ | `200` + заголовок `X-LP-Stale: 1` | старый ответ | показывает; строка «Источник» может сказать «кэш» |
| то же, кэша нет | `502` | `{"error":true,"reason":"upstream"}` | сбой |
| наш лимит исчерпан | `429` + `Retry-After` | — | сбой, повтор позже |

Формат тела ошибки Open-Meteo **мерено**: `400`, `{"error":true,"reason":"Latitude
must be in range of -90 to 90°. Given: 999.0."}`. Приложение и сегодня не читает
тело ошибки: любой не-JSON-ответ = `DecodingError` = сбой.

### 2.5 Лимиты Open-Meteo (из доки)

Бесплатно: 600 в минуту, 5 000 в час, **10 000 в день**, 300 000 в месяц; «без
гарантии доступности»; право блокировать IP без предупреждения.
Один запрос = 1 «вызов» до 14 суток и 10 переменных; больше — дробный вес
(в доке: 15 переменных × 2 недели = 1,5; 4 недели = 3,0). Наш прогноз —
11 переменных × 21 сутки: по пропорции вес **≈ 1,65** (формулу доки применил я,
не мерено); воздух — 2 переменные × 5 суток = 1. Итого **≈ 2,65 вызова на одно
место при промахе кэша**. Потолок бесплатного дня: 10 000 / 2,65 ≈ **3 700 разных
точек в сутки**.

**Главное следствие для прокси.** Все пользователи из РФ будут приходить в
Open-Meteo с одного IP (выходной адрес Yandex Cloud, общий пул) и делить одну квоту.
Её же могут вычерпать соседи по пулу — риск из доки, не мерено. Поэтому кэш по
округлённой точке обязателен, а не оптимизация.

**Коммерция (важно, из доки Open-Meteo, terms).** Бесплатный API — «только для
некоммерческого использования»; приложение с подпиской или рекламой названо
коммерческим и должно брать платный план; донаты в тексте не упомянуты
(«из доки, не мерено» как будет трактовано). План монетизации — год донатов, затем сайт + покупка в
приложении (память `light-plan-monetization-plan`): **к моменту, когда появятся
платежи, бесплатный API перестаёт подходить**, и это касается не только прокси, но и
напрямую (бета/веб). Цену платного плана не вытаскивал (страница `pricing` отдала
только бесплатные лимиты) — смотреть https://open-meteo.com/en/pricing.
Ещё: данные CC BY 4.0 — в приложении нужна строка источника (в вебе она есть,
`index.html:8335`; в нативе — шаг 3, «Источник»).

## 3. Защита от чужих запросов

Честно: **в публичном приложении секрет не бывает секретным** — всё, что лежит в
сборке (ключ, адрес), достаётся из `.ipa`. Поэтому защита — слоями, а держит только
последний.

| слой | что даёт | чего не даёт |
|---|---|---|
| Фиксированные параметры (§ 2.2) | чужой не заказывает через нас другие переменные и сроки | не мешает гнать любые точки |
| Валидация и округление точки | кэш работает, мусор отсекается | — |
| Ключ приложения в заголовке `X-LP-Key` (значение — в настройках сборки; в функции — в Lockbox, ~20 ₽/мес за версию секрета — из памяти `yandex-cloud-ru-home`, не перемерено) | отсекает случайных ботов и сканеры; ключ можно **сменить** выпуском приложения и держать два действующих | не останавливает того, кто распаковал `.ipa` |
| **Лимиты вызовов** | верхняя граница денег и квоты Open-Meteo, даже если ключ утёк | не отличает своего от чужого |
| Бюджет в консоли | письмо при превышении (ресурсы сам **не** останавливает — из памяти `yandex-cloud-ru-home`) | не защита |
| App Attest (Apple) | подтверждает, что вызывает настоящее приложение | нужен серверный разбор подписи; возможность на бесплатной команде **не проверена** (часть возможностей — iCloud, Push, WeatherKit — на ней недоступна, `docs/17` § 12) |

**Лимиты, которые реально держат:**
1. Предел параллельных вызовов функции (настройка функции, `concurrency`/квота
   облака — из доки, значение выбрать в шаге 2).
2. Свой счётчик в функции: N запросов с одного IP в минуту (память экземпляра —
   грубо, но дёшево) и **общий дневной потолок обращений в Open-Meteo** (напр.
   6 000 вызовов; при превышении — только кэш и просроченные ответы). Он защищает
   квоту Open-Meteo, а значит и всех пользователей, от одного нарушителя.
3. Квоты облака на число вызовов функции (при необходимости снижаются запросом).

**Предложение:** ключ + фиксированные параметры + дневной потолок на Open-Meteo.
App Attest — только если появятся реальные злоупотребления (сложно, нужен сервер).
**Lockbox для одного ключа** — решить, нужен ли он на старте: значение можно
положить в переменную окружения функции (видна всем, у кого есть доступ к
каталогу, но не в репозитории). Lockbox — ~20 ₽/мес; для одного человека
в каталоге выигрыш небольшой.

**Приватность** (из кода): строка `NSLocationWhenInUseUsageDescription` сегодня
обещает: «Ничего не отправляется никому, кроме названия места на серверы Apple».
Open-Meteo сегодня получает координаты прямо с телефона (без идентификаторов, но с
IP); с прокси координаты (округлённые) и IP уходят в **Yandex Cloud**, дальше в
Open-Meteo — уже с IP облака (телефона там нет). Текст в настройках сборки
(`native/Config/iOS.xcconfig:21`) устарел и до этого — Open-Meteo в нём не назван;
править в шаге 3 и показать Алексею (В3).

бесплатных ≈ **45 ₽**; вызовы укладываются в бесплатный миллион; трафик
≈ 10 ГБ (мерено на размерах) — в бесплатных 100. Промах кэша стоит дороже — функции
ждёт Open-Meteo: чем выше доля попаданий, тем ниже счёт. Пример (допущение, не мерено): 1 000 ежедневных пользователей × 3 места ×
2 вызова × 30 дней = 180 тыс. вызовов в месяц — ≈ 1/5 бесплатного миллиона.
Вывод: **до десятков тысяч пользователей прокси
укладывается в бесплатный объём или рубли в месяц**; узкое место — не деньги, а
10 000 вызовов в день Open-Meteo (§ 2.5) и их коммерческие условия.

## 7. Как приложение переключается (для шага 3)

- **Адрес из настроек сборки:** новый ключ `WEATHER_PROXY_URL` в
  `native/Config/Shared.xcconfig` → `Info.plist` (`INFOPLIST_KEY_…` не годится для
  своих ключей — нужен `Info-iOS.plist`, где уже лежит своя схема `lightplan://`) →
  `OpenMeteoSource(proxy: URL?)`. Ключ `X-LP-Key` — рядом, но **не в репозитории**:
  репозитории публичны (правило 28) — в локальном `.xcconfig`, не попадающем в git.
  Пустой адрес = прямой Open-Meteo, поведение сегодняшнее.
- **Откат на прямой:** порядок «прокси → при сбое прямой Open-Meteo» (прокси чаще
  доступен из РФ, из остального мира оба работают; ответ один формат). Без VPN в РФ
  прямой не поможет, но сбой прокси не должен оставлять без прогноза тех, кто
  вне РФ. Дублирование запроса при сбое прокси — ценой лишней секунды таймаута;
  таймаут прокси — короче (предложение 8 с вместо 60 по умолчанию).
- **Повтор:** сегодня сбой молчаливый и вечный (`catch { return }`, § 1.3).
  Нужно (предложение): (1) повтор при возврате приложения на экран — `scenePhase ==
  .active` (в `RootView.swift:35` `onChange(of: scenePhase)` уже есть, но только на
  `.background`); (2) пока `isLive == false` — повтор раз в 3–5 минут, пока экран
  открыт, с растущей паузой; (3) смена места сбрасывает счётчик; (4) успех гасит
  повторы. Кэш `WeatherFetcher` сбой не хранит — повтор дойдёт до сети.
- **Строка «Источник»:** «Open-Meteo через сервер Light Plan» / «прямой Open-Meteo» /
  «расчёт, прогноз недоступен» — для честности (выдумка не должна выглядеть
  прогнозом); к тому же CC BY 4.0 требует имени источника.
- **Хвосты шага 3:** тест на сценарий «прокси недоступен → прямой → оба
  недоступны → выдумка → вернулись → прогноз»; `PointWeather` повторяет те же правила.

## 8. Открытые вопросы к Алексею

Только продуктовые и денежные; технические выбраны в § 2, 6, 7.

**В1. Что делать, когда Open-Meteo станет платным (подписка/покупки в приложении).**
Free-API Open-Meteo — «только для некоммерческого использования», подписка и
реклама названы коммерческими. У тебя в плане год донатов, потом сайт + покупка.
- (а) Платить Open-Meteo с первого платежа (план у них есть, цену я не достал —
  смотреть на странице). **Плюс:** без риска блокировки и юридически чисто. **Минус:**
  постоянные деньги, ещё до того как приложение заработало.
- (б) Остаться на бесплатном и считать донаты «не коммерческим». **Плюс:** 0 ₽. **Минус:**
  в их условиях донаты не названы прямо, а блокируют без предупреждения — риск
  выключенного прогноза у всех в РФ (прогноз — сердце балла заката).
- (в) Через год перейти на другой источник (WeatherKit — на бесплатной команде
  не проверялся, нужен платный Apple Developer). **Плюс:** без счёта Open-Meteo.
  **Минус:** новая работа, и ярусы облаков у WeatherKit не проверены.
- **Мой выбор: (а), но решение — к моменту первого платежа**; сейчас прокси
  работает и на бесплатном, а я записываю риск и дату пересмотра.
