# Как поднять сервер ядра: срез 1 (к выпуску Light Plan)

Инструкция для Алексея и для сессии ядра (Event OS). Что нужно от сервера и зачем,
описано в `light_plan:Light_Plan/docs/core_requirements_2026-11-19.md` (CORE-01, CORE-02,
CORE-03, вопрос 4.7). Здесь только **как это построить**. Обозначения:
- **[Алексей]** — делаешь руками в консоли: аккаунты, секреты, платные ресурсы;
- **[сессия]** — пишет код и выкладывает;
- **«не мерено»** — взято из памяти или из кода, перед решением проверить.

---

## 0. Что строим, в двух словах

Не «сервер» в смысле арендованной машины, а **набор функций без машины** (serverless).
Это тот же образец, по которому уже работают прогноз погоды (`lightplanweather`) и
админка студии (`tomsonadmin`), и тот, что записан в `ws:INDEX.md` → Region mirrors:
«Worker → Cloud Functions, KV → YDB».

| | Россия (номера +7 и СНГ) | Мир (остальные номера) |
|---|---|---|
| Код | Yandex Cloud Function, Node.js, вызов напрямую (без API Gateway: он дорогой) | Cloudflare Worker |
| Записи устройств | YDB serverless, одна таблица | Workers KV |
| Аватарки | Object Storage, закрытый бакет | R2, закрытый бакет |
| Секрет-соль | Lockbox (или переменная функции, как у погоды) | секрет Worker'а |
| Каталог / аккаунт | каталог `eventos` (уже есть, пустой) | аккаунт Cloudflare (уже есть) |

**Код один.** Вся логика (проверка ID, пропуск, проверка JPEG, ответы) — общий модуль на
JavaScript. Каждому дому — тонкая прослойка, которая подставляет своё хранилище. Так оба дома
не разъедутся.

**Почему без машины:** не нужно её обновлять и сторожить, запросов будет мало (десятки
в день), а у обоих облаков есть бесплатная квота. Квоты на память (из памяти, **не мерено**,
сверить с тарифами): Workers — 100 тыс. запросов в день; KV — 100 тыс. чтений и 1 тыс.
записей в день; R2 — 10 ГБ; Yandex Functions — 1 млн вызовов в месяц; YDB serverless —
бесплатный объём; Object Storage — копейки за мегабайты. Аватарка ≈ 50 КБ: 1000 фотографов —
50 МБ.

> **Нужно слово Алексея (правило 7):** «без машины, как погода» — да или нет. Если нет,
> выбор между ВМ и Serverless Containers остаётся открытым, как записано в требованиях.

## 1. Что делает Алексей руками (один раз)

Порядок важен: секреты появляются до кода, в репозиторий не попадают никогда.

**Мир (Cloudflare):**
1. [Алексей] Workers & Pages → Create → Worker с именем `eventos-core`. Код пока не нужен.
2. [Алексей] Storage → KV → Create namespace `eventos-devices`.
3. [Алексей] R2 → Create bucket `eventos-avatars` (публичный доступ выключен — это вариант по
   умолчанию). Если R2 попросит карту, это бесплатный тариф с картой: решать тебе.
4. [Алексей] В Worker'е: Settings → Variables and Secrets → Secret `PASS_SALT`. Значение —
   длинная случайная строка. Её можно получить в терминале командой ниже и вставить, никому
   не показывая:
   ```bash
   openssl rand -hex 32
   ```
5. [Алексей] Привязки (Bindings) в Worker'е: KV `DEVICES` → `eventos-devices`; R2 `AVATARS` →
   `eventos-avatars`.

**Россия (Yandex Cloud, каталог `eventos`):**
6. [Алексей] Managed Service for YDB → Создать базу → **Serverless**, имя `eventos-core`.
7. [Алексей] Object Storage → бакет `eventos-avatars` с **закрытым** доступом на чтение
   (не путать с бакетом-сайтом `eventos`, он публичный).
8. [Алексей] Сервисный аккаунт `eventos-core` с ролями: `ydb.editor` на базу,
   `storage.editor` на бакет. Других ролей не нужно: функция вызывается публично.
9. [Алексей] Cloud Functions → функция `eventoscore`, Node.js 22, сервисный аккаунт из п. 8,
   **публичная** (как `lightplanweather`). Переменная окружения `PASS_SALT` — **другая** строка
   из `openssl rand -hex 32` (у домов разные соли).
10. [Алексей] Записать в `ws:INDEX.md` → Region mirrors, строка `event_os`: что создано.
    Это может сделать сессия по твоим словам, но адреса и имена — только то, что ты видел
    в консоли.

Ключей, паролей, соли и телефонов в репозиторий не кладём: репозитории открытые.

## 2. Что пишет сессия ядра

**Где:** `event_os:server/` в репозитории Event OS (в своей ветке-worktree, как у Light Plan).

```
server/
  core/            общий модуль: маршруты, проверки, ответы — без облака
    routes.js      /v1/health, /v1/devices, /v1/devices/me, /v1/me/avatar, /v1/me
    id.js          проверка ID id7XXXXXXXXXX (та же формула, что в приложении)
    pass.js        выдача пропуска и проверка по хешу
    jpeg.js        проверка JPEG и вырезание метаданных
  cloudflare/      Worker: хранилище = KV + R2; wrangler.toml без секретов
  yandex/          функция: хранилище = YDB + Object Storage
  test/            тесты общего модуля на подложном хранилище
```

**Хранилище — одна маленькая «розетка»**, которую реализует каждый дом:
`getDevice(deviceId)`, `putDevice(rec)`, `deleteDevice(deviceId)`,
`listDevicesById(appId)`, `getAvatarMeta(appId)`, `putAvatar(appId, bytes, meta)`,
`deleteAvatar(appId)`. В KV для поиска по ID держать отдельный ключ `byId:<хеш appId>` →
список устройств. В YDB — две таблицы, `devices` и `avatars`.

### 2.1 Пропуск (CORE-01)
- `POST /v1/devices`: проверить ID (`400 bad_id`, если номер не мобильный); создать
  `deviceId = "dv_" + 16 случайных байт`, `pass` = 32 случайных байта (base64url).
  **Хранить только** `HMAC-SHA256(PASS_SALT, pass)`, сам пропуск — нет. Ответ `201` —
  единственный раз, когда пропуск уходит из сервера.
- Любой запрос с пропуском: заголовок `X-Core-Pass: <pass>` → посчитать HMAC → найти устройство.
  **Не `Authorization`:** шлюз Яндекса проверяет его как IAM-токен даже у публичной функции и
  отвечает 403, не пуская запрос в функцию (замер 24.11: `Bearer fake123` → 403, `X-Core-Pass` → 200).
  Нет — `401 bad_pass`. Сравнение — за постоянное время (`crypto.subtle` / `timingSafeEqual`).
- `PATCH /v1/devices/me`: смена номера — перенести аватарку на новый ID, у старого пометка
  «переехал».
- `DELETE /v1/devices/me`: стереть устройство; если у ID других устройств нет, стереть и
  аватарку.

### 2.2 Аватарка (CORE-02)
- `PUT /v1/me/avatar` (по пропуску), тело — JPEG.
  Проверки по порядку: размер ≤ 1 МБ (`413`); первые байты `FF D8` (`415`); размеры из
  заголовка SOF: квадрат, сторона 256–1024 (`422`).
- **Вырезать метаданные без перекодирования:** пройти по сегментам JPEG и выбросить
  `APP1`–`APP15` (там EXIF, геометка, XMP) и `COM`. Это разбор байтов, без библиотек
  картинок: одинаково работает в Worker'е и в функции. Настоящее перекодирование
  (библиотека `sharp`) есть только в Яндексе, в Worker'е его нет → **решение сессии
  (вывод оркестратора):** в обоих домах только вырезание, требование «перекодировать»
  в CORE-02 заменить на «вырезать метаданные». Телефон уже отдаёт JPEG 512 без геометки.
- Ключ в хранилище: `avatars/<avatarKey>/<версия>.jpg`, где `avatarKey` = HMAC от ID (не
  сам номер). Сначала записать новую версию, потом стереть старую («Стирать сразу»).
- `GET /v1/me/avatar`: байты, `ETag` = sha256, `304` на `If-None-Match`, `404 none`.
- Чтение чужими по ID номера («Все, кто знает номер»): `POST /v1/avatars/lookup` с телом
  `{"id":"id7…"}` — ID в теле, не в адресе (принцип «В адресах нет личного»: адреса попадают
  в журналы). Отдаёт, только если номер подтверждён (CORE-05, после выпуска). **До CORE-05 этот путь
  всегда даёт 404**, и это правильно.
- `DELETE /v1/me/avatar` → `204`.

### 2.3 «Удалить мои данные» (вопрос 4.7)
- `DELETE /v1/me` по пропуску → стереть все устройства этого ID, аватарку, отметки
  «переехал». Повтор → `204`. В приложении это кнопка «Удалить мои данные · телефон, фото».

### 2.4 Связь (CORE-03)
- `GET /v1/health` без пропуска → `{"ok":true,"core":"0.1.0","home":"ru"|"world","time":…,"api":["devices","avatar"]}`.
  В `api` — только разделы, которые уже работают: приложение не зовёт то, чего нет.

### 2.5 Общее
- Ответы — JSON, ошибки `{"error":"bad_pass"}` с кодами из требований.
- Ограничение частоты (`429`): на первое время — не больше 30 запросов в минуту с одного
  пропуска, счётчик в KV / YDB.
- **В журналах нет телефонов, ID и пропусков.** Только `deviceId` и код ответа.
- **Маршруты в Яндексе:** путь после адреса функции не проходит (замер 24.11: `/v1/health` →
  400 «invalid functionID»). Раздел выбирается параметром: `?op=health`, `?op=devices` и т. д.

## 3. Порядок работ и проверка

Каждый шаг — отдельный коммит. После каждого — проверка `curl` в **обоих** домах
(правило 21).

| Шаг | Что | Проверка |
|---|---|---|
| 0 | `GET /v1/health` в обоих домах | `curl -s <адрес>/v1/health` → `"ok":true` и свой `home` |
| 1 | `POST/DELETE /v1/devices` | регистрация даёт `201` и пропуск; испорченный пропуск — `401`; после `DELETE` — `401`; городской номер — `400 bad_id` |
| 2 | `PUT/GET/DELETE /v1/me/avatar` | загрузка 512×512 → `GET` отдаёт тот же sha256; 2 МБ → `413`; PNG → `415`; 400×300 → `422`; JPEG с геометкой → обратно без неё (`exiftool`); замена → старый ключ `404` |
| 3 | `PATCH /v1/devices/me`, `DELETE /v1/me` | смена номера переносит аватарку; после `DELETE /v1/me` — `401` и `404` |
| 4 | Тесты общего модуля в CI | зелёные на каждом пуше |

Тестовые номера для проверок — только выдуманные, не настоящие.

**Затем Light Plan:** когда шаги 0–3 зелёные в обоих домах, ядро пишет адреса двух домов в
хаб (`platform_hub:QUEUE/lightplan.md`). Сессия Light Plan подставляет их вместо «сервера
нет» (клиент уже есть, `6db44f18`), проверяет на телефоне и **в тот же день меняет подпись
конфиденциальности** «не храним на сервере ничего личного» (принцип «Подпись меняется в день
запуска»).
