# Свет в окнах зала — справка для BroniOS

Шаг 31в, 08.10.2026. Решение Алексея: «Свет в окнах зала. Важная задача, нужна
реализация сегодня» (DECISIONS 08.10). Хозяин правила — Light Plan; BroniOS и
сайт студии берут копию и проходят наши эталоны (договорённость от 07.10).

## Что делает правило

По месту зала, моменту времени и стороне, куда смотрят окна, отвечает одним из
пяти слов:

| `kind` | слово | когда |
| --- | --- | --- |
| `direct` | прямой | солнце над горизонтом и светит в окна |
| `golden` | закатный | то же, но солнце низкое и тёплое (золотой час); `half` = `evening` или `morning` |
| `diffuse` | рассеянный | солнце в окна не светит: за стеной, у самого горизонта, ниже него, ночью |
| `none` | нет окон | `hasWindows = false` |
| `unknown` | нет данных | чего-то не хватает (`reason`); значение не выдумывается |

**Подпись функции: «по солнцу, без погоды».** Облака правило не смотрит:
«прямой» значит «солнце стоит так, что светит в окна», а не «в зале будет
солнечно». Честно так и показывайте: «по расчёту солнца, погода не учтена».

## Что НЕ учтено

- **Погода** — в этой версии нет.
- **Размер окна** — не учитывается.
- **Преграды** — дом напротив, деревья, козырёк, жалюзи.
- Глубина зала: куда луч дойдёт по полу.
- Преломление света в воздухе (как и в солнечной модели Light Plan).

Правило отвечает на вопрос «смотрит ли солнце в эти окна», а не «насколько
светло в зале». Для «закатного» слова направление окон решает больше, чем
кажется: в Томске окно на запад получает вечерний закатный свет каждый день
года (365 из 365), окно на юг — в 190 днях из 365 и ни разу летом: закатное
солнце летом стоит на северо-западе, мимо южного окна (перебор по минутам).

## Как BroniOS берёт файл

Копировать **один файл** `light_plan:Light_Plan/tools/window_light.js` (ни DOM,
ни браузерных API, ни зависимостей; нужен только стандартный `Intl` — он есть
в браузере и в Node). Подключение:

```js
const WindowLight = require("./window_light.js");      // Node
// <script src="window_light.js"></script>             // браузер: появится window.WindowLight

const r = WindowLight.at({
  instant: "2026-10-08T14:00:00+07:00",   // слот брони: ISO со сдвигом, Date или миллисекунды
  lat: 56.4847, lon: 84.9482,             // координаты студии
  timezone: "Asia/Tomsk",                 // hall.timezone
  hasWindows: true,                       // hall.hasWindows
  windowsAzimuth: 180                     // hall.windowsAzimuth — куда СМОТРЯТ окна
});
// r.kind → "direct" | "golden" | "diffuse" | "none" | "unknown"
// WindowLight.LABELS_RU[r.kind] → «прямой» / «закатный» / «рассеянный» / «нет окон» / «нет данных»
```

Вход:

| поле | что | если нет |
| --- | --- | --- |
| `instant` | момент: `Date`, число мс с 1970, строка ISO **с явным сдвигом** (`+07:00` или `Z`) | `unknown / bad_moment`. Строка без сдвига отвергается намеренно: её читают по поясу машины, и ответ зависел бы от того, где запущен код |
| `lat`, `lon` | координаты студии, градусы (север и восток положительны), числа | `unknown / no_coordinates` (также вне диапазона) |
| `timezone` | имя пояса зала по IANA | `unknown / no_zone`; имени нет в базе — `bad_zone` |
| `hasWindows` | строго `true` или `false` | `unknown / no_windows_flag` |
| `windowsAzimuth` | куда смотрят окна, градусы от севера по часовой (0 север, 90 восток, 180 юг, 270 запад); любое число, приводится к 0…360 (`-90` = `270`, `360` = `0`) | `unknown / no_azimuth`. Строка `"180"` — не число: приведите сами |

`hasWindows: false` даёт `none` и без остальных полей. Порядок проверок —
сверху вниз по таблице, первая нехватка и называется в `reason`.

Выход: `{ kind, reason, half, sunElevation, sunAzimuth, offsetFromWindow }`.
`reason` есть только у `unknown`, `half` — только у `golden`. Числа — градусы:
высота солнца, азимут солнца, угол между азимутом солнца и азимутом окон
(0…180). У `none` и `unknown` числа равны `null`.

Сутки и минуты считаются по часам зала: правило само берёт сдвиг пояса на
этот момент, летнее время учитывается. Утро/вечер `half` — до и после
солнечного полудня.

Нужны ещё `WindowLight.THRESHOLDS` (три порога), `WindowLight.REASONS` (слова к
`reason`), `WindowLight.NOTE` («по солнцу, без погоды»).

## Пороги — выбор исполнителя, Алексей может подправить

Три числа, заданы константами в начале `window_light.js` и в
`WindowLight.swift` (`minElevation`, `goldElevation`, `maxOffset`):

| порог | значение | почему |
| --- | --- | --- |
| `minElevation` | **2°** | Ниже солнце у самого горизонта: луч идёт через самый толстый слой воздуха и закрыт любым забором, а преград мы не знаем. «Заметно выше нуля» из постановки. |
| `goldElevation` | **6°** | Верх золотого часа в солнечной модели Light Plan (`goldA`/`goldB` = высота 6°). Между 2° и 6° — «закатный» (с `half`: утренний тоже тёплый), выше 6° — «прямой». |
| `maxOffset` | **85°** | Окно «ловит» солнце, если азимут солнца отличается от азимута окон не больше, чем на 85°. 90° — плоскость стены: луч идёт вдоль неё и в зал не попадает. Пять градусов запаса — на такой скос луч только скользит по откосу. |

Как они двигают ответ (Томск, минуты с солнцем в окнах за сутки, измерено
перебором по минутам; столбцы — окна на восток / юг / запад):

| порог | 20 марта | 21 июня | 21 декабря |
| --- | --- | --- | --- |
| принятые 85° и 2° | 327 / 673 / 328 | 491 / 539 / 492 | 153 / 350 / 154 |
| угол 80° | 310 / 626 / 311 | 479 / 494 / 480 | 132 / 350 / 132 |
| угол 90° | 344 / 688 / 344 | 503 / 586 / 504 | 175 / 350 / 175 |
| высота 0° | 342 / 673 / 342 | 512 / 539 / 512 | 175 / 393 / 175 |
| высота 3° | 320 / 673 / 320 | 482 / 539 / 482 | 141 / 326 / 142 |

Пять градусов угла сдвигают сутки на 15–50 минут, градус высоты — на 10–40
(больше всего зимой). Это размер ошибки от выбора порога, а не от модели.

Пример для ориентира (Томск, 21 июня, окна на запад): света в окнах 492 минуты
с 13:34 до 21:45, из них закатный — последние 37. Окна на юг в тот же день:
08:53–17:51, закатного нет совсем.

## Как сверять

Числа сверки: `light_plan:native/Fixtures/window_light.json` (репозиторий
`LightPlan`, публичный; после слияния ветки — `main`). Это 9597 ответов: 8 мест
(Томск, Москва, Сочи, нуль широты, Мурманск и Лонгйир — полярные день и ночь,
Сидней — южное полушарие, Катманду — некруглый пояс) × 8 дат (оба солнцестояния
и равноденствия, переводы часов Европы и Сиднея, 29 февраля) × моменты (каждый
час 25 часов от полуночи зала — через полночь и перевод часов, плюс по полминуты
вокруг прохождений солнцем 2° и 6°) × окна на 0 / 90 / 180 / 270 / 137.5°;
пробы порога угла (±84.99° и ±85.01° от азимута солнца, в том числе через
обёртку 360°) и случаи «нет данных».

Своя копия проходит их одной командой:

```
node tools/window_light_check.js <путь к window_light.json> [<путь к вашей копии>]
```

Код 0 — копия считает так же, как приложение Light Plan; код 1 — расходится, в
выводе первые расхождения. Допуски: ответ строго, высота и азимут солнца
`1e-9°`. Скрипт сверяет и пороги из паспорта фикстуры: сменили порог у себя —
увидите сразу. Не правьте числа сверки руками: они пересобираются
(`make parity` в `native`), расхождение — ошибка копии, пока не доказано
обратное.

Как держится правда: стенд Light Plan при каждом прогоне пересчитывает солнце
каждой строки блоками, вырезанными из живой беты, и падает, если копия в
`window_light.js` разошлась с ней больше чем на `1e-9°` (на сегодня худшее
расхождение `1e-13°`). Swift-версия (`WindowLight.swift`) проходит те же числа
в тестах. Порча проверена: поменять знак азимута окон, порог угла, порог
высоты или пояс — тесты Swift, сверка JS и сам стенд падают.

Если Light Plan поменяет порог или солнечную модель, файл и числа сверки
обновятся вместе — берите оба.
