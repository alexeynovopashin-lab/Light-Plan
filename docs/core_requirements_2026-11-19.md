## 0. Для Алексея (полстраницы)

**Где мы сейчас.** Живого сервера ядра нет: в Event OS есть документы и демо-страницы, которые читают данные из браузера и в сеть не ходят (`core_link` «Главное» п.1). Всё, что Light Plan «получает от ядра», сегодня — файл со списком студий, вложенный в сборку (п.8). По сети приложение ходит в сервер BroniOS (связь с бронью) и в наши функции Яндекса (погода, читалка Pinterest) — это не ядро.

**Что ядро должно уметь к выпуску Light Plan** (ваши слова 19.11: «перед релизом нам надо добавить возможность загружать аватарки и чтобы они были доступны ядру»; «Только своя»):
1. **Узнать телефон фотографа.** Когда фотограф с планировщиком нажимает «загрузить фото», ядро заводит для этого телефона «пропуск» — длинный пароль, который телефон хранит сам и показывает при каждом запросе (CORE-01).
2. **Принять и хранить аватарку** фотографа: одну картинку, своё фото, а не клиентов (CORE-02).
3. **Отвечать «я на связи»** по одному адресу в России и в мире — чтобы и приложение, и мы могли проверить связь с ядром (CORE-03; ваши слова 19.11 «проверить связь с ядром в целом»).
Всё это — в двух домах: Яндекс для России, Cloudflare для остального мира (правило 22 `ws:CLAUDE.md`).

**После выпуска:** список студий с сервера вместо файла в сборке, подтверждение номера кодом, данные залов для «света в окнах», счётчики в ваш дашборд, уведомления. **Будущее:** бронь через ядро (этап 6), общий формат `/v1/`, ИИ, события-матрёшки и команда, полевой режим.

**Решено раньше вами и не обсуждается заново:** один ID по номеру телефона на всю платформу (A-009); ID только адресует и ничего не доказывает (§1 моста); чужая запись в данные фотографа — только предложение, применяется после его «да» (§3); у организации своего адреса нет (§6); событие — матрёшка (§12); полевой режим — журнал на каждом устройстве (§11); телефон нужен только тем, кто пользуется планировщиком (A-014); бронь до этапа 6 живёт в воркере BroniOS (Q-014).

**Открыто, решаете вы** (раздел 4): ждёт ли выпуск сервер ядра; кто видит аватарку; чем подтверждать номер (почта номер не подтверждает); в каком доме лежит аватарка; откуда приложение берёт список студий.

### К выпуску

#### CORE-01 · Пропуск устройства и ID фотографа

- **Приоритет:** к выпуску (без него аватарка ничья).
- **Зачем:** ядро должно знать, чья аватарка. Решено: «у нас есть единая система ID по номеру телефона» (Алексей 08.10, A-009 — `platform_hub:DECISIONS.md` 2026-10-08); ID ничего не доказывает, устройство получает долгий пропуск (`event_os:BRIDGE_BRONIOS.md` §10.2, стр. 645–670; `platform_hub:docs/PLATFORM_ARCHITECTURE.md` «Вход по ID»). Там же решено: «пока номер не подтверждён, канал работает, а администратор видит пометку "номер не подтверждён"» — на этом и строится выпуск.
- **Light Plan шлёт:** свой ID `id7XXXXXXXXXX` (как в «Профиле»: `light_plan:native/Packages/LightPlanUI/Sources/LightPlanUI/App/AppModel+Profile.swift:46`), страну номера, версию приложения. Имя — только если человек его ввёл (`me.name`, там же, стр. 27–31). Город — нет.
- **Получает:** непрозрачный `deviceId`, секрет-пропуск (один раз), состояние ID (`unconfirmed`), дом записи.
- **API (предложение):**
  - `POST /v1/devices` → `{"app":"lightplan","appId":"id7XXXXXXXXXX","country":"RU","appVersion":"1.0 (123)","name":"Алексей"}` → `201 {"deviceId":"dv_…","pass":"<секрет>","idState":"unconfirmed","home":"ru"}`.
  - `PATCH /v1/devices/me` (смена номера в «Профиле») → `{"appId":"<новый>","previous":"<старый>","at":"2026-11-19T10:00:00Z"}`; ядро переносит аватарку на новый ID, старый ID отмечает «переехал» (повторяет цепочку `me.ids` на телефоне, `AppModel+Profile.swift:52-60`).
  - `DELETE /v1/devices/me` → `204`: «забыть это устройство», стирает пропуск и, если других устройств у ID нет, аватарку.
  - Заголовок всех запросов с пропуском: `Authorization: Bearer <pass>`.
  - Ошибки: `400 bad_id` (не мобильный или не тот вид), `401 bad_pass`, `429 rate_limited`, `503 unavailable`.
- **Хранилище:** запись устройства: `deviceId`, хеш пропуска (сам пропуск не хранится), `appId`, страна, дом, `idState`, `createdAt`, `lastSeen`, версия приложения. Размер — сотни байт. Срок: удалять устройство, не появлявшееся 12 месяцев (предложение). Россия — YDB serverless, мир — KV (`ws:INDEX.md` Region mirrors); пропуск-секрет сервера (соль) — Lockbox / секрет Worker.
- **Воркер / фон:** чистка устройств старше срока — раз в сутки.
- **Доступ:** сам пропуск. Несколько неподтверждённых устройств с одним ID допустимы и друг друга не видят (защита от «занял чужой номер первым»: до подтверждения чужие данные не показываются никому, кроме своего устройства). После подтверждения (CORE-05) прочие неподтверждённые устройства этого ID гаснут.
- **Конфиденциальность:** номер внутри ID — личные данные; лежит только в доме записи. Регистрация — только действием человека (нажал «загрузить фото» или «подключиться к ядру»), только у тех, кто сам ввёл свой мобильный (A-014). Любитель «Света» не регистрируется.
- **Регионы:** обе версии одинаковы; дом выбирается по стране номера (вопрос 4.4). Ядро в другом доме знает только «такой ID есть, он живёт в ru» — справочник, не содержимое.
- **Как Light Plan проверит:** (1) регистрация с телефона из РФ даёт `home: ru`, запись видна в YDB, в KV её нет; с номером другой страны — наоборот; (2) запрос с испорченным пропуском — `401`; (3) `DELETE` и повторный запрос — `401`; (4) номер не мобильный — `400 bad_id`. Плюс тест на подложном сервере в самом приложении.
- **Статус:** п.15 — ID считается локально, сервера ID нет; регистрации и кода нигде нет (`core_link`).

#### CORE-02 · Аватарка фотографа (только своя)

- **Приоритет:** к выпуску — единственный пункт, который Алексей сам назвал условием выпуска (`core_link` п.20).
- **Зачем:** Алексей 19.11: «перед релизом нам надо добавить возможность загружать аватарки и чтобы они были доступны ядру»; на «Чьи аватарки загружаем?» — «Только своя» (`light_plan:Light_Plan/DECISIONS.md:26262-26268`). 15.11: «аватарки нужны для ядра, там EventOS может использовать их для команд потому это важно» (`light_plan:Light_Plan/DECISIONS.md:26009`). Вопрос ядру — Q-062 (`platform_hub:QUEUE/eventos.md:214`), ответа нет. Сегодня на месте аватарки кружок с инициалами (`light_plan:native/Packages/LightPlanUI/Sources/LightPlanUI/Screens/Settings/SettingsRoot.swift:59,88`).
- **Light Plan шлёт:** квадратный JPEG 512×512, до 300 КБ, без EXIF (без геометки и модели камеры), обрезанный на телефоне. Круг — только отрисовка, хранится квадрат.
- **Получает:** версию, хеш, размеры; картинку назад — своему устройству.
- **API (предложение, это и ответы на Q-062 п.1–2):**
  - `PUT /v1/me/avatar`, `Content-Type: image/jpeg`, тело — байты, заголовок `If-Match: <версия>` (по желанию) → `200 {"avatar":{"version":3,"sha256":"…","w":512,"h":512,"bytes":48211,"updatedAt":"…"}}`.
  - `GET /v1/me/avatar` → байты (`ETag` = sha256; `304` на `If-None-Match`); `404 none`, если аватарки нет.
  - `DELETE /v1/me/avatar` → `204`.
  - Для чужих глаз (команды, студии — когда появятся, вопрос 4.2): `GET /v1/avatars/{avatarKey}?v=3` по короткой подписанной ссылке, которую ядро выдаёт тому, кому показывать можно. `avatarKey` непрозрачен, не содержит ID и телефона. Нет права — `404`, как будто аватарки нет (не выдаёт, что она есть).
  - Ошибки: `401 bad_pass`, `413 too_large`, `415 bad_type` (не JPEG), `422 bad_size` (не квадрат, сторона меньше 256 или больше 1024), `409 version_conflict`, `429`, `503`.
- **Хранилище:** закрытый бакет (без публичного чтения): Россия — Yandex Object Storage, мир — Cloudflare R2. Ключ объекта — `avatars/<avatarKey>/<версия>.jpg`, без телефона. Плюс уменьшенная копия 128×128. На человека — 1 текущая версия; старая стирается сразу после записи новой (вопрос 4.6). Удаление аватарки — объект стёрт в течение суток. Ориентир объёма: 1 000 фотографов × ~60 КБ ≈ 60 МБ (оценка, не мерено).
- **Воркер / фон:** при записи — проверить, что это JPEG нужного размера; перекодировать заново (вырезает EXIF, даже если телефон его оставил); сделать копию 128. Раз в сутки — стереть объекты без живой записи.
- **Доступ:** писать и читать свою — только по пропуску (CORE-01). До подтверждения номера (CORE-05) аватарку не видит никто, кроме своего устройства и ядра.
- **Конфиденциальность:** лицо — личные данные; лежит в доме записи. Нужна правка страницы конфиденциальности и ответов App Store в день запуска (принцип выше). Закон о персональных данных (152-ФЗ) для фото лица — не проверено.
- **Регионы:** обе версии; разрыв не допускается (иначе у фотографа из мира аватарки нет).
- **Как Light Plan проверит:** (1) загрузка 512×512 → `GET` отдаёт тот же sha256; (2) файл 2 МБ → `413`; PNG → `415`; 400×300 → `422`; (3) JPEG с геометкой → скачанный назад без EXIF (проверка `exiftool`/`sips`); (4) замена → старая версия по старому ключу `404`; (5) `DELETE` → `GET` даёт `404`; (6) аватарка номера РФ лежит в Яндексе и отсутствует в R2; (7) чужой пропуск не читает чужую аватарку.
- **Статус:** п.20 — только в документах; принимающей стороны нет; договора об аватарках в хабе нет (`core_link` противоречие 8).

#### CORE-03 · «Ядро на связи»

- **Приоритет:** к выпуску, мелкий.
- **Зачем:** Алексей 19.11: «проверить связь с ядром в целом» (`light_plan:Light_Plan/DECISIONS.md:26264`). Сегодня проверять нечего: получателя нет (`core_link` «Что нельзя проверить»).
- **API:** `GET /v1/health` без пропуска → `200 {"ok":true,"core":"0.1.0","home":"ru","time":"2026-11-19T10:00:00Z","api":["devices","avatar"]}`. Поле `api` — какие разделы уже есть: приложение не зовёт то, чего нет.
- **Хранилище / воркер:** нет.
- **Регионы:** оба адреса; Light Plan зовёт адрес своего дома, при отказе — второй.
- **Как Light Plan проверит:** `curl -so /dev/null -w "%{http_code}" <адрес>/v1/health` = 200 в обоих домах (правило 21 `ws:CLAUDE.md`); в приложении — строка диагностики «Ядро: на связи / нет связи» (без влияния на работу).
- **Статус:** сервера нет.

## Найденные противоречия между источниками

1. **Адрес студии.** `event_os:BRIDGE_LIGHT_PLAN.md` §9 (решено 03.09) и ответ ядра на Q-023: адрес студии = `pl` + её мобильный. `event_os:16_Place_Registry.md` («Модель записи места», «Выдача номеров»): `pl` + число, не связанное с телефоном (в файле 06.11 — `pl100001` у «Томсона»), а `pl`+телефон — только подсказка (`aliases`). Мост не исправлен.
2. **Имена полей окон.** Договоры (`window_light.md`, Q-024, Q-032): `hasWindows`, `windowsAzimuth`. Отдаваемый файл 06.11: `windows`, `azimuth` (замер полей файла). Приложение не читает ни те, ни другие.
3. **Подтверждение номера почтой** (`event_os:BRIDGE_BRONIOS.md` §10.2, Алексей 09.10) не доказывает владение номером, а `platform_hub:docs/PLATFORM_ARCHITECTURE.md` «Вход по ID» называет код «доказательством, что номер в руках». Вопрос 4.3.
4. **Где живёт ядро.** `platform_hub:docs/PLATFORM_ARCHITECTURE.md` §2а, §6а: «Делаем её один раз, в Яндекс Облаке»; реестр мест — только Яндекс. Правило 22 `ws:CLAUDE.md` и `ws:INDEX.md`: каждая служба в двух домах. Мировой копии ядра в документах ядра нет — разрыв не записан в `ws:INDEX.md`.
5. **Источник списка студий.** Алексей 05.11: «С сервера BroniOS» (`light_plan:Light_Plan/DECISIONS.md:25405`); ядро: файл — объект в бакете Яндекса, строится реестром (`event_os:16_Place_Registry.md`); это задание называет его «отдаёт ядро». Вопрос 4.5.
6. **Аватарка к выпуску.** Алексей 19.11: «перед релизом… доступны ядру». Вывод оркестратора в тот же день: «передача ядру — когда у ядра будет сервер (Q-062 открыт)» (`light_plan:Light_Plan/DECISIONS.md:26277`). Это два разных условия выпуска. Вопрос 4.1.
7. **Подпись конфиденциальности.** Алексей 29.08: «не храним на сервере ничего личного, даже id» (`light_plan:Light_Plan/DECISIONS.md:10748`) — CORE-01/02 это меняют; правку подписи надо выпустить в тот же день.
8. **Дом для России у доп-сервера Light Plan.** `event_os:BRIDGE_LIGHT_PLAN.md` §7: «VK — приоритетно для РФ»; §11: «на Яндексе (или VK)»; `ws:INDEX.md` (Алексей 18.09): Россия = Yandex Cloud. К ядру прямо не относится, но мост устарел.
9. **Старые расхождения из описи** (не новые): Q-001 и Q-002 не исполнены в коде, `window_light.md` пишет «Swift не слит», хотя он в `main` (`platform_hub:CONFLICTS.md` C-005; `core_link` «Противоречия» 1–5).

Не проверено в этом документе: работа воркеров BroniOS и функций Яндекса (не запускались); законы о персональных данных; условия App Store; цены облаков; поведение Telegram при «поделиться контактом».
