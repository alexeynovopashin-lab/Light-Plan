# Справка 28м.1 — ссылки и доски Pinterest: воркер беты, перенос в Yandex Cloud, натив

Итерация 28м, шаг 1 (03.10.2026). Кода приложения и выкладки нет; облако не менялось (только `yc … list/get`).
Пометки: **мерено** — выполнено 03.10 с этого Mac (curl, Mac вне российской сети: доступность из РФ
этим не проверяется); **из кода** — прочитано в `og-reader/worker.js`, `beta/index.html`, `native` (main), не
запускалось; **из доки** — публичные страницы Pinterest / Yandex Cloud; **не мерено** — оценка.
Пути: `light_plan:Light_Plan/…` (веб, репозиторий `Light-Plan`), `light_plan:native/…` (натив).

## 0. Одной картинкой

```
beta (PWA) ──?url= / ?board= / ?img=──▶ Cloudflare Worker light-plan-og-reader ──▶ pinterest.com, pin.it, i.pinimg.com
                                         (без ключа, без кэша, CORS *)             (og:image, внутренний resource-API)
native     ── ничего не запрашивает: «Ссылка» кладёт плитку «сайт + хвост пути» без картинки
```

Цель 28м: то же самое для натива через `lightplanogreader` (Yandex Cloud), потому что с мобильного
интернета без VPN `www.pinterest.com` и `pin.it` не открываются (проба 03.10, `docs/network_diag/results_2026-10-03.md`),
а Yandex Cloud отвечает за 0,3–0,8 с.

**Главные находки справки:**
1. Воркер беты — **открытый прокси**: `?url=` и `?img=` берут **любой** http(s)-адрес. В Yandex-функции это
   дыра (функция может позвать адрес метаданных облака) — нужен белый список хостов (§ 3.2).
2. Доска режется на 100 пинах **молча**: постраничного чтения нет, клиент `pinCount` с числом пинов не сверяет (§ 1.4).
3. Все картинки доски воркер отдаёт размером **736 px** (мерено, 6 из 6) — экранная копия «1600» в бете на деле 736 (§ 1.3).
4. У Pinterest условия запрещают автоматический сбор без разрешения, `robots.txt` для «чужих» ботов — `Disallow: /`,
   `/resource/` закрыт для всех, кроме Google и нескольких поисковиков (§ 5). Это **риск, а не решённый вопрос**.
5. Достаёт ли Yandex Cloud до Pinterest — **неизвестно**; без этого шаги 2–3 строить рано (§ 3.1).

## 1. Что делает воркер беты (`og-reader/worker.js`, 288 строк)

Представляется честно: `User-Agent: LightPlanLinkPreview/1.0 (+https://alexeynovopashin-lab.github.io/Light-Plan/)`.
Ничего не хранит и не логирует; ключа нет; CORS `*`; `GET` и `OPTIONS`, остальное — `405`; любая
непойманная ошибка — `500 "error"`. Адрес беты: `light-plan-og-reader.alexeynovopashin.workers.dev`
(`beta/index.html:13526`).

### 1.1 Три режима (из кода)

| запрос | что делает | ответ |
|---|---|---|
| `?url=<страница>` | `fetch` страницы (`accept: text/html`, `redirect: follow`), потоково через `HTMLRewriter` ищет `og:image`, `og:image:secure_url` или `twitter:image`, обрывает чтение на первом найденном; таймаут 8 с; затем качает саму картинку | `200` байты + `content-type` оригинала; `404` нет тега / картинка не отдалась / не `image/*`; `400` нет `url` или схема не http(s) |
| `?board=<ссылка>` | раскрывает короткую ссылку, читает доску (§ 1.2), собирает список | `200` JSON `{name, pinCount, pins:[{id, permalink, image}]}`; `400` `{"error":"bad url"}` / `{"error":"not a board url"}`; `404` `{"error":"board not found"}` |
| `?img=<адрес картинки>` | качает байты как есть | `200` байты, `cache-control: public, max-age=86400`; `404` не отдалась / не картинка; `400` плохой адрес |

Мерено (03.10, Mac, доска «Коллектив» `pin.it/3qVvzLDZl`): `?board=` → `200`, 2,0 с, 1 095 байт, 6 пинов,
`pinCount: 6`; `?img=` одного пина → `200`, 0,75 с, 69 781 байт, `image/jpeg`; `?url=<пин>` → `200`, 1,17 с,
те же 69 781 байт (то есть og:image пина = картинка 736x, та же, что в списке доски); `?board=` с `example.com/a/b` → `400`.
Значит форма ответа в § 3 — не гипотеза, а снятая с живого воркера.

### 1.2 Что читается у Pinterest

- **Одиночный пин** — HTML-страница пина, только метатеги в `<head>` (контракт «превью для мессенджеров»,
  `docs/15_MOODBOARD.md` «Ссылка становится картинкой»).
- **Доска** — внутренний resource-API сайта (не OAuth v5; тот чужую публичную доску не перечисляет):
  1. `GET <origin>/resource/BoardResource/get/?data={"options":{"field_set_key":"detailed","username":U,"slug":S},"context":{}}`
     → `resource_response.data.id` и `.name`, `.pin_count`.
  2. `GET <origin>/resource/BoardFeedResource/get/?data={"options":{"board_id":ID,"board_url":"/U/S/","page_size":N},"context":{}}`
     → `resource_response.data[]` — пины; из каждого берётся `images["736x"]`, иначе `474x`, `236x`, `orig`.
  3. Заголовок **`x-pinterest-pws-handler: www/[username]/[slug].js`** — без него сервер отвечает `403` всем
     (по комментарию в коде; не перепроверял), заголовок «опознавательный», не секрет.
  `<origin>` — тот хост, что в ссылке (`www`, `ru`, `pinterest.ru`…): воркер ходит туда же, куда указала ссылка.
- **Раскрытие коротких ссылок** (`pin.it/<код>` → `api.pinterest.com/url_shortener/<код>/redirect/` →
  `pinterest.ru/<user>/<board>/?invite_code=…`): до пяти шагов вручную (`redirect: manual`, читает `location`),
  останавливается, как только адрес стал узнаваемой доской, саму страницу не запрашивает. `api.*` доской не считается.
- Доской считается путь из двух сегментов, где первый не `pin`; третий сегмент (раздел доски) игнорируется.
  Хост — `pinterest.<что угодно>` (проверка `(^|\.)pinterest\.[a-z.]+$`).

### 1.3 Что воркер отдаёт и чего не отдаёт

- Ссылка пина — всегда `https://www.pinterest.com/pin/<id>/` (не тот хост, что в исходной ссылке).
- **Размер — 736x** (первый из списка предпочтений; мерено 6/6). Оригинал (`orig`) берётся только если нет
  ни 736x, ни 474x, ни 236x. Для просмотра на телефоне 736 px по длинной стороне — мало при увеличении
  (в бете `BLOB_S = 1600`, но источник 736: экранная копия просто не больше исходной).
- Нет: описания пина, автора, названия, цвета, размеров картинки (`w`/`h` клиент снимает сам из байтов), страницы раздела.

### 1.4 Лимиты, кэш, ошибки

- **Потолок 100 пинов**: `page_size = min(pin_count, 100)`, **закладки (`bookmark`) для следующей страницы нет** —
  доска на 150 пинов отдаст первые 100 без сообщения; `pinCount` в ответе правдивый (150), но клиент его не сверяет
  (`fetchOgBoard`, `beta/index.html:13562`). Живые доски Алексея: 95 и 90 пинов — в потолок влезают.
- **Кэша у воркера нет**: каждый запрос — заново к Pinterest. Единственный кэш — `cache-control: max-age=86400` на байтах
  картинки (кэш браузера клиента). Для `?board=` заголовка кэша нет.
- **Защиты нет**: ни ключа, ни лимита на IP, ни потолка в день.
- **Ошибки**: любой сбой Pinterest (403, таймаут, не JSON) для доски — `404 board not found`, для картинки — `404`;
  клиент не отличает «Pinterest заблокировал» от «доски нет».
- Одиночный `pin.it`-пин: клиент сначала пробует как доску (`?board=` → `400`), потом `?url=` — два запроса вместо одного.

### 1.5 Чем рискует

| риск | почему | что с этим |
|---|---|---|
| Внутренний API Pinterest меняется или закрывается | не документирован, не гарантирован (`docs/15_MOODBOARD.md` «Доски») | принято Алексеем осознанно; запасной путь — одна обложка через `og:image`, честная строка «Доска не открылась целиком» |
| Бан по IP | запросы идут с одного адреса за всех; у Cloudflare это пул Cloudflare, у Yandex Cloud будет пул Yandex Cloud — **ни тот, ни другой не ведёт себя как домашний IP** | не мерено; проба § 3.1 |
| Открытый прокси | `?url=`/`?img=` без проверки хоста | в функции — белый список (§ 3.2) |
| Условия Pinterest | § 5 | вопрос Алексею (В4) |

## 2. Что делает бета с ответом (`beta/index.html`)

### 2.1 Распознавание ссылок

`askUrl` (`:23907`): обрезать, без `http(s)://` дописать `https://`. Дальше `addLinkTo` (`:20783`) — **одна дверь на все
подборки** (форма съёмки, набор жанра, папка мудборда). Решает `isPinterestBoardUrl` (`:13543`):

| ссылка | считается | что дальше |
|---|---|---|
| `pin.it/<что-то>` | **доска** (пробуем как доску: короткая ссылка не говорит, куда ведёт) | воркер раскрывает; пин → `400` → клиент падает на `?url=` |
| `pinterest.<tld>/<user>/<board>/…` (2+ сегмента, первый не `pin`), любой поддомен: `www.`, `ru.`, `pinterest.ru` | доска | `?board=` |
| `pinterest.<tld>/pin/<id>/` | не доска → обычная ссылка | `?url=` (og:image) |
| `pinterest.<tld>/<user>/` (профиль, 1 сегмент) | обычная ссылка | `?url=` — картинка профиля, если есть |
| любой другой сайт | обычная ссылка | `?url=` (поэтому Instagram и любой сайт тоже получают og:image) |

### 2.2 Одиночная ссылка (`one`, `:20793`)

Сначала карточка-ссылка ложится в подборку **сразу** (`k:"link"`, `url`, `tags`), картинка догоняет:
`fetchOgImage` → байты → `refShots` (два размера в IndexedDB: превью 200 px, экранная 1600 px; `BLOB_T/BLOB_S`, `:13378`) →
запись получает `im, w, h`. Нет сети / нет og:image — остаётся текстовая карточка. Кадр могли убрать, пока воркер ходил — проверка `shotById`.

### 2.3 Доска (`fetchOgBoard`, `:13562`)

1. `?board=` → JSON. Нет пинов / ошибка → `onFail` → строка «Доска не открылась целиком — легла одной обложкой»
   (`mb.boardOne`, есть в 5 языках в `beta/lang.js`) + один кадр через `one(url)`. Строка показывается, только если у двери есть место под неё (`o.note`).
2. Для **каждого** пина (все до 100, либо `limit` у посева) сразу, **параллельно, без очереди**:
   `?img=<image>` → блоб → `refShots` → `onPin(shot, pin)`.
3. `onPin`: подборку убрали, пока ехало — `blobDrop`; **дубль** узнаётся по пину (`url === pin.permalink` среди кадров подборки,
   потому что «Скопировать ссылку» в приложении Pinterest каждый раз даёт новый инвайт) — байты выбрасываются; иначе
   `shotAdd({k:"link", url: permalink, im, w, h, tags})` + `boardPut`; пины ложатся по мере готовности, а не списком.
4. **Чего нет**: индикатора прогресса, кнопки отмены, повтора упавших пинов (ошибка одного пина глотается `catch(function(){})`),
   сверки `pinCount` с числом принятых, лимита по размеру/месту, сообщения «принято N из M». Всё это для натива новое.
5. Параллель без ограничения — для воркера Cloudflare безразлично, для функции Yandex с ограничениями — нет (§ 3.4).

## 3. Перенос на Yandex Cloud

### 3.1 Проба «достаёт ли Yandex Cloud до Pinterest» — план (САМ не выполнял)

Нужна временная функция (шаг 2 по слову Алексея). Тот же приём, что § 5 справки погоды (`docs/weather_proxy_reference.md`).
1. Временная функция `lightplanogreadertest` в каталоге `lightplan`, без секретов, 15 строк Node: `fetch` пяти адресов,
   в ответ — статус, время, первые 200 байт, заголовки `server`/`cf-ray`/`x-pinterest-*` (если есть):
   (а) страница пина `https://www.pinterest.com/pin/115264071708018540/` (доска «Коллектив»);
   (б) `BoardResource` для известной доски (с заголовком `x-pinterest-pws-handler` и **без** него — чтобы знать, что именно он даёт);
   (в) `BoardFeedResource` той же доски;
   (г) `https://pin.it/3qVvzLDZl` с `redirect: manual` — цепочка до доски;
   (д) байты `https://i.pinimg.com/736x/…jpg` из ответа (г/в).
2. С Mac `curl` на ссылку функции: коды, время, размеры. Критерий «да»: (а)(б)(в)(д) — `200`, JSON разбирается, размер картинки совпадает с замером § 1.1 (69 781 байт для того же пина).
3. С телефона Алексея без VPN, на мобильном интернете (Safari по ссылке функции, она отдаёт текст отчёта): тот же результат. Это главный замер: он же измерит, как быстро Яндекс отдаёт ответ в белом списке.
4. Повторить трижды в разное время суток (исходящий IP функции может меняться — не мерено) и ещё раз после 20–30 минут простоя (холодный старт).
5. Не заработало (Pinterest отвечает `403`/капчей на IP дата-центра Яндекса) — **стоп, вопрос Алексею**. Запасные пути: (а) прямой путь с телефона там, где он есть (одиночный пин: `og:image` + `i.pinimg.com`; доска — только если телефон достаёт `www.pinterest.com`, то есть на Wi-Fi); (б) ВМ с постоянным IP (~1 300 ₽/мес, из памяти `yandex-cloud-ru-home`, не перемерено) — дороже и тот же риск бана; (в) только «Поделиться»/вставка картинки из буфера руками.
Перед стартом пробы убедиться, что временная функция удаляется в конце, а в журналах нет ссылок на чужие доски.

### 3.2 Функция `lightplanogreader` (Node.js 22, без зависимостей, по образцу `lightplanweather`)

Образец, **прочитан из облака 03.10**: функция `lightplanweather` (`d4ed8g9iaj0to6t9dne7`, ACTIVE, каталог `lightplan`),
`nodejs22`, `index.handler`, память 128 МБ, таймаут 30 с, `concurrency` 8, единственная переменная окружения `LP_KEY`
(значение не читал). Код `light_plan:Light_Plan/yandex/lightplanweather/index.js`: проверка `X-LP-Key` через `timingSafeEqual`
по sha256, кэш в памяти экземпляра, per-IP 60 в минуту, дневной потолок `DAILY_CAP`, `429` с `Retry-After`.
Прямая ссылка `https://functions.yandexcloud.net/<id>` (путь после id не принимается — режимы идут через query).

**Запрос — те же три параметра, что у воркера беты**, чтобы клиент менялся только адресом и заголовком:

```
GET <base>?board=<ссылка>   → JSON {name, pinCount, pins:[{id, permalink, image}]}   (как § 1.1; + см. ниже «добавки»)
GET <base>?url=<страница>   → байты og:image
GET <base>?img=<адрес>      → байты картинки
заголовок X-LP-Key: <ключ приложения>
```

**Добавки к ответу (без поломки клиента беты)**: `truncated: true`, если у доски пинов больше, чем в списке (§ 1.4);
`X-LP-Cache: hit|miss|stale`, как у погоды; тело ошибки `{error:true, reason}` вместо голых строк (`not a board url`,
`board not found`, `upstream`, `forbidden`). Отличать «Pinterest не ответил» (`502 upstream`) от «такой доски нет»
(`404`) — клиенту нужно для честной надписи (§ 4.4).

**Безопасность (новое, у воркера беты этого нет):**
- **Белый список хостов, обязательный.** Принимаются только `pinterest.<tld>`, `pin.it`, `api.pinterest.com` (шаг короткой
  ссылки), `i.pinimg.com`. Без него функция — открытый прокси к любому адресу, включая метаданные облака
  (служебный IP, из которого берётся токен сервисного аккаунта функции). Проверять хост **на каждом переходе редиректа**
  (редиректы вручную, как в `resolveShort`), а не только на входе; запретить IP-адреса и порты, кроме 443.
- Ключ `X-LP-Key` — тот же приём, что у погоды: значение в переменной окружения функции и в локальном
  `.xcconfig` вне git (репозитории публичные). Тот же ключ или отдельный — техническое, предлагаю **отдельный**
  (`LP_KEY` у `lightplanogreader`), чтобы утечка одного не открывала второй.
- Размер: `?img=` принимает только `image/*` и не больше ≈ 5 МБ (потолок; **из доки/памяти: тело ответа функции ограничено
  несколькими МБ — не мерено, проверить в шаге 2**); `?url=` читает HTML потоково и обрывает после `</head>` или на 1 МБ.
- Заголовок для Pinterest — тот же честный `User-Agent: LightPlanLinkPreview/1.0`; `x-pinterest-pws-handler` как в воркере.
- Журнала адресов не вести: в логах функции — только код, время, режим (без ссылок и без IP).

### 3.3 Кэш

Цель: не ходить в Pinterest дважды за то же и не тянуть чужие картинки в наше облако.
- **JSON доски** — память экземпляра, срок ≈ 10 мин (ту же доску часто вставляют второй раз; Pinterest-запросов вдвое меньше).
  Ключ — `username/slug` в нижнем регистре (не ссылка: у инвайтов она разная). Предложение, не замерено.
- **Раскрытие `pin.it`** — память, ≈ 1 ч (код → адрес доски/пина не меняется).
- **Картинки — в наш бакет не кладём** (мой выбор, В3): хранение чужих картинок у нас — отдельный юридический вопрос (§ 5), а выигрыша
  мало — каждую картинку человек качает один раз и хранит у себя. На ответе `?img=` остаётся `cache-control: public, max-age=86400`
  (кэш клиента, как у воркера беты).
- Опора на память экземпляра ненадёжна (холодный экземпляр = пустой кэш) — как у погоды; бакет-кэш не нужен, пока замер шага 2 не покажет обратное.

### 3.4 Потолок вызовов

Доска из N пинов = 1 вызов `?board=` + N вызовов `?img=` (до 101). Погодные пределы (60 в минуту на IP, `concurrency` 8) для
этого малы: бета открывает все 100 картинок разом.
- **Клиент натива ходит за картинками ограниченно** (предлагаю 4–6 одновременно), а не всеми сразу — иначе упрёмся в
  per-IP-тормоз функции и в Pinterest.
- **Per-IP на `lightplanogreader`**: ≈ 240 вызовов в минуту (доска на 100 пинов укладывается с запасом), предложение.
- **Дневной потолок обращений в Pinterest** на экземпляр (напр. 3 000; при превышении — `429` + `Retry-After`) — защищает
  от бана IP и от счёта; значения меняются константами без выкладки приложения.
- Метрика «картинок на доску»: живые доски Алексея — 6, 7, 8, 9, 15, 15, 15, 17, 90, 95 пинов (память «Доски Pinterest»).

### 3.5 Цена (из доки, не мерено)

Тарифы те же, что в `docs/weather_proxy_reference.md` § 4 (Yandex Cloud, РФ, ₽ с НДС, 02.10): вызовы 1 млн в месяц бесплатно,

### 4.2 Что добавить (набросок для шагов 3–4, на согласование)

1. **Распознавание ссылки** — чистая функция в Domain (рядом с `RefLink`): `PinterestLink.kind(url) → .pin | .board(user, slug) | .short | .other`, правила — ровно § 2.1

2. **Один пин (ссылка → превью).** Кадр-ссылка кладётся сразу, как сегодня (честная плитка), картинка догоняет: `?url=` (при `.short` — функция раскрывает
   одним запросом; **не** пробовать сначала как доску, как делает бета) → байты → `RefImageStore.save` → `RefFrame` получает `im`, `w`, `h`, `mt`.
   Новая операция Domain: «приложить картинку к кадру» (`attachImage(im:w:h:to:)`), с проверкой, что кадр ещё жив и `im` не занят.
3. **Вся доска.** После `?board=` — **лист подтверждения перед закачкой**: «Доска «<имя>» · N пинов · ≈ M МБ, добавить?» (предложение; см. В1) и

   Дубль — по permalink, как в бете (§ 2.3); перед закачкой дубли отфильтровать — не тратить трафик.
4. **Запись в модель.** Ровно как в бете: `RefFrame(kind: .link, url: permalink, im: <новое имя>, w, h, tags: [раздел], mt)` + `put` в подборку.

   Пишем пачками (каждые ≈ 5–8 пинов один `mbEdit`), а не 80 раз по одному `persist` (из кода — 80 записей снимка подряд; не мерено, стоит проверить в шаге 3).
5. **Откат на прямой путь** (если 28л.6 это потребует): одиночный пин — `og:image` страницы и `i.pinimg.com` напрямую (стабильный контракт, 40 строк Swift);

   Исключение — только если проба § 3.1 покажет, что Yandex не достаёт Pinterest: тогда решение выносится Алексею.

## 5. Юридическое и этическое

**Читал 03.10 (публичные страницы, без догадок; юридической консультации это не заменяет):**
- **Условия использования** (`policy.pinterest.com/en/terms-of-service`), разд. 2(a): запрещено «scrape, collect, search, copy or otherwise access data or content from Pinterest in unauthorized ways, such as by using automated means (without our express prior permission)». Разд. 3(a): пользователь сохраняет права на то, что публикует. Разд. 3(b): Pinterest и пользователи получают широкую лицензию на сохранение и показ контента — **нам такая лицензия не выдана**.
- **Правила разработчиков** (`policy.pinterest.com/en/developer-guidelines`), разд. «What not to do»: запрещено собирать данные автоматическими средствами, кроме явно разрешённого; разд. «Publishing content»: связывать пины с источником на Pinterest и ясно показывать, что контент оттуда; разд. «The basics»: **нельзя хранить информацию, полученную через материалы Pinterest, включая API**. Это правила для пользователей **официального** API; наш путь — не официальный API, но применять к нему более мягкие стандарты оснований нет.
- **`robots.txt`** (`pinterest.com/robots.txt`, снят 03.10): для общего агента `User-agent: *` — `Disallow: /`; для Googlebot и ряда поисковиков — разрешено `Allow: /resource/*/get/` (то есть именно тот путь `…/resource/BoardResource/get/`), для остальных — `Disallow: /resource/`. Наш `User-Agent: LightPlanLinkPreview/1.0` не назван → под `*`. **Мы читаем то, что для таких агентов закрыто.**
- **Что в нашу пользу (контекст, не оправдание):** `og:image` на странице пина публикуется для превью в чужих чатах (контракт), `pin.it` и «Поделиться» созданы для передачи ссылок; читаем только публично доступное, без логина, по одному запросу от человека, ничего не храним на сервере, представляемся честно.

**Вывод:** формально это **автоматический доступ без разрешения Pinterest** — нарушение условий возможно. Практический риск — не иск, а блокировка IP функции
(§ 1.5) и, если приложение попадёт в App Store, замечание на ревью. Решение принимает Алексей (В4); справка не утверждает, что это «законно» или «незаконно».

**Что показываем пользователю.** Источник и авторство: пин остаётся **кадром-ссылкой** с `url = https://www.pinterest.com/pin/<id>/` — по тапу «Открыть на Pinterest»
(`openURL`); в просмотрщике — подпись «Pinterest» и эта кнопка (сегодня её нет, § 4.1). Имя автора пина воркер не отдаёт — не показываем. Картинка — это
референс для себя на съёмке, не публикуем и не отдаём дальше (в экспорте съёмки — только ссылка, **вопрос**: в «Поделиться съёмкой» картинка пина должна попадать? — не решено).
**Хранение чужих картинок:** на телефоне пользователя (`attachments/`) — он сам нажал «добавить», это личная копия референса; **в нашем облаке не храним**, кроме транзита
через функцию (как у воркера). Это совпадает с твоим предположением. Нюанс: при будущей облачной синхронизации (итерация 30) файлы `attachments/` пойдут в **личное** облако пользователя (Яндекс/Google/Dropbox) — не наше;
это надо не забыть в тексте об ограничениях.

## 8. Шаг 28м.3 — что показала живая проверка клиента (04.10.2026)

Клиент натива (`native`, ветка `wt/28m`) прошёл против настоящей читалки (`LP_LIVE_OG=1 swift test --filter PinterestLive`, ключ из файла вне репозитория) и в симуляторе на тестовой доске «Коллектив» (6 пинов, `pin.it/3qVvzLDZl`).

- **Короткая ссылка: сначала доска, потом пин** (поправка к § 4.2 п. 2). - **Заглушка на мёртвой короткой ссылке** (**мерено**): `?board=` на `pin.it/<опечатка>` — `400 not a board url`, а `?url=` на ту же ссылку — **`200` и общая картинка Pinterest** (PNG 921 610 байт, мозаика с красной «P»; один и тот же sha256 `32a37cba…240c` у двух разных несуществующих кодов). Хрупко: если Pinterest сменит заглушку, фильтр её не узнает — тогда добавить новый отпечаток. Настоящий несуществующий `/pin/<номер>/` даёт честный `404` (мерено).
