# EventOS — итог обсуждения

## 1. Общая концепция

EventOS развивается не как набор отдельных CRM-приложений, а как универсальная объектная система:

**ядро + специализированные планы/ветки + подключаемые коннекторы.**

Важный вывод: Core необязательно проектировать заранее.

Вместо модели:

`Core → приложения`

может оказаться более правильной эволюция:

`LightPlan + BakerPlan + MakeupPlan + FloristPlan + EventPlan + Micro Plans → общий Core`

То есть ядро постепенно **выявляется из пересечения реальных веток**.

---

## 2. ID как фундамент

В EventOS уже введена система ID:

- у каждого пользователя есть User ID;
- каждому заказу присваивается Order ID;
- разные сущности можно связывать через ID.

Это снимает необходимость определять отношения через комбинации имени, даты, названия и других косвенных признаков.

Например:

```text
EVENT-ID 74291
│
├── ORDER-ID 18342 — Engagement Session
├── ORDER-ID 18357 — Wedding
└── ORDER-ID 18411 — Post-Wedding Session
```

Каждый Order остаётся самостоятельным объектом, а связь с Event определяется отношением между ID.

---

# 3. Event, Order и Client

Постепенно проявляются три разных уровня.

### Client / User

Участник долгосрочных отношений.

### Event

Контекст, объединяющий связанные работы и участников.

Пример:

`Wedding — Anna + Max`

### Order

Конкретная работа, которую необходимо выполнить.

Например:

- Engagement Session;
- Wedding Day;
- Post-Wedding Session;
- Anniversary Session.

Важный принцип:

> **Event может закончиться, а отношения с клиентом продолжаются.**

---

# 4. EventOS как граф объектов

Организатор может объединить в одном EventOS пространстве большое количество исполнителей.

Например:

```text
EVENT-ID 74291
Wedding: Anna + Max
│
├── Organizer
├── Photographer → LightPlan
├── Videographer
├── Baker → BakerPlan
├── Florist → FloristPlan
├── Makeup → MakeupPlan
├── DJ / MC
├── Driver → Driver PWA
├── Venue
└── другие исполнители
```

Каждый исполнитель может иметь:

- собственный User ID;
- собственные Orders;
- собственные задачи;
- собственные файлы;
- собственный Plan;
- собственные специализированные инструменты.

При этом все они могут быть связаны с одним Event ID.

---

# 5. Организатор

Организатор — особая роль.

Им может быть:

- невеста;
- жених;
- свадебный агент;
- координатор;
- другой человек, собирающий событие.

Организатор не обязан заставлять всех устанавливать отдельное приложение.

Многие роли получают просто специализированную PWA.

Например:

### Фотограф

Полноценный LightPlan.

### Кондитер

BakerPlan.

### Водитель

Минимальная PWA:

- время;
- адрес;
- контакт;
- маршрут;
- статус.

### Организатор

Получает агрегированное представление всего события.

Идея:

> **Один Event → множество специализированных представлений → единый граф объектов и связей.**

---

# 6. LightPlan

LightPlan — самый сложный существующий Plan и фактически стресс-тест архитектуры.

У него:

### 4 слоя временных итераций

- день;
- неделя;
- месяц;
- год.

### 2 слоя внешних зависимостей

- погода;
- свет / астрономические условия.

LightPlan проверяет:

- работу с разными масштабами времени;
- пересчёт представлений;
- зависимости;
- внешние данные;
- сложное планирование.

Поэтому новые ветки не обязательно должны иметь такую сложность.

---

# 7. BakerPlan

Кондитер выбран не случайно:

1. есть реальный тестировщик модели — знакомый, занимающийся бенто-тортами;
2. модель кондитера похожа на фотографическую;
3. при этом внутренняя структура достаточно отличается, чтобы проверить универсальность EventOS.

---

## 7.1. Заказ

Один клиент может оформить один заказ с несколькими разными тортами.

Например:

```text
ORDER-ID 5101
│
├── Cake 01 → мама → адрес A
├── Cake 02 → жена → адрес B
└── Cake 03 → сестра → адрес C
```

Каждый торт может иметь:

- своего получателя;
- свой адрес;
- своё время;
- свой состав;
- свой референс;
- свою цену;
- свою техкарту.

При этом Order остаётся единым контейнером.

Это аналогично тому, как одна съёмка является самостоятельным Order, а Event может объединять несколько Orders.

---

# 8. Техкарта

Для домашнего кондитера техкарта — одна из центральных сущностей.

iPad может использоваться как рабочий экран непосредственно на кухне.

Техкарта должна быть не PDF-документом, а интерактивной рабочей поверхностью.

Пример:

```text
ФИСТАШКА — МАЛИНА
Выход: 2 кг

КОРЖ
☐ Яйцо — 240 г
☐ Сахар — 180 г
☐ Мука — 180 г
☐ Фисташковая паста — 60 г

КОНФИ
☐ Малина — 400 г
☐ Сахар — 80 г
☐ Пектин — 12 г

КРЕМ
☐ Маскарпоне — 500 г
☐ Сливки — 300 г
☐ Сахарная пудра — 100 г
```

Вес должен автоматически масштабировать ингредиенты:

- 1,5 кг → ×0,75;
- 2 кг → ×1;
- 3 кг → ×1,5.

При добавлении рецепта в Order должна использоваться конкретная версия техкарты.

Изменение базовой техкарты не должно задним числом изменять уже принятый заказ.

---

# 9. BakerPlan и фотографическая модель

В фотографии:

`Order → съёмка → жанр → референсы → локация → выполнение`

У кондитера:

`Order → торт → тип → техкарта → состав → референсы → производство → выдача`

То есть структура похожа, но внутренняя логика различается.

Это именно тот тип различия, который должен проверять EventOS:

> одинаковое ядро, разные профессиональные модели.

---

# 10. FloristPlan

Ветка флориста практически неотличима от BakerPlan.

Это полезно для архитектуры.

Если две профессии используют почти одинаковую модель, не обязательно создавать два разных приложения.

Различия могут находиться в:

- справочниках;
- терминологии;
- специализированных полях;
- коннекторах;
- UI.

---

# 11. MakeupPlan

MakeupPlan может быть почти прямой адаптацией существующей фотографической ветки.

Возможный подход:

- отключить ненужное;
- переименовать классы;
- изменить терминологию;
- оставить общий механизм Orders, клиентов, дат, файлов, задач и связей.

То есть многие ветки могут быть не новыми приложениями, а **тонкими вертикальными адаптерами**.

---

# 12. Ветка ведущего

Ведущий может использовать урезанную модель фотографа.

Ему могут быть нужны:

- Order;
- Client;
- дата;
- площадка;
- тайминг;
- программа;
- контакты;
- задачи;
- файлы;
- коммуникация.

При этом большая часть фотографических функций не нужна.

---

# 13. Ветка водителя

Водитель — пример Micro Plan.

Полноценное приложение ему не требуется.

Организатор может раздать PWA:

```text
10:30
Забрать Анну
Адрес: ...

14:00
Hotel → Venue

18:30
Venue → Hotel
```

Минимальный набор:

- время;
- адрес;
- маршрут;
- контакт;
- статус.

Это показывает, что не каждая роль должна получать самостоятельное приложение.

---

# 14. Американская свадьба как архитектурный стресс-тест

Американская свадьба особенно хорошо подходит для EventOS, поскольку представляет собой сеть независимых исполнителей:

- planner / coordinator;
- photographer;
- videographer;
- baker;
- florist;
- makeup artist;
- DJ / MC;
- venue;
- caterer;
- transportation;
- rentals;
- lighting / AV;
- officiant и т. д.

Один Event объединяет множество профессионалов.

Каждый работает в собственной области, но все связаны общим Event ID.

Организатор видит агрегированное состояние события.

Это почти буквальная реализация философии:

> **одно событие → множество профессиональных контуров → одно ядро связей.**

---

# 15. Американская и СНГ-модель свадьбы

Условно:

### США / Европа

Свадьба чаще организована как проект:

`Event → Organizer → Independent Vendors → Timeline`

Много независимых исполнителей:

- фотограф;
- видеограф;
- флорист;
- кондитер;
- визажист;
- DJ;
- транспорт;
- venue и т. д.

### СНГ

Исторически большее значение имеет единое мероприятие и банкет:

`Wedding → ведущий / тамада → гости`

Ведущий часто управляет социальной динамикой вечера:

- тосты;
- поздравления;
- конкурсы;
- танцы;
- интерактив;
- переходы между частями программы.

В американской модели DJ/MC может управлять reception, но обычно не является координатором всей свадьбы.

Для EventOS американская структура удобнее как архитектурный пример, поскольку она естественным образом образует сеть независимых пользователей и заказов.

---

# 16. Свадьба как несколько Orders

Одна свадьба может содержать несколько самостоятельных заказов фотографа.

Например:

```text
EVENT-ID
Wedding Anna + Max
│
├── ORDER-ID
│   Engagement / Couple Session
│
├── ORDER-ID
│   Wedding Day
│
└── ORDER-ID
    Post-Wedding Session
```

Также сюда могут относиться:

- LoveStory;
- Couple Session;
- Anniversary Session;
- другие связанные съёмки.

Это подтверждает полезность разделения:

**Event ≠ Order.**

---

# 17. Post-Wedding Session и Trash the Dress

Важно различать два понятия.

### Post-Wedding Session

Общая категория отдельной послесвадебной фотосессии.

Она может проходить:

- на следующий день;
- через несколько дней;
- через недели;
- во время honeymoon;
- в другом городе;
- в другой стране.

### Trash the Dress

Более специфическая концепция послесвадебной съёмки, исторически связанная с более экстремальным использованием свадебного наряда.

Это не синоним любой Post-Wedding Session.

В 2010–2013 годах Trash the Dress был заметным свадебным фототрендом, но в EventOS правильнее моделировать именно более широкую сущность Post-Wedding Session.

---

# 18. Жизненный цикл клиента фотографа

Клиент может проходить длинный цикл:

```text
CLIENT-ID
│
├── LoveStory
├── Wedding
├── Anniversary +1 year
├── Anniversary +2 years
└── Family Session
```

Таким образом, EventOS может хранить не только историю заказов, но и контекст отношений.

---

# 19. Follow-up и повторные продажи

В практической фотографической работе использовалась модель:

1. LoveStory со скидкой для будущей свадебной пары.
2. Wedding.
3. В день передачи материала — напоминание о специальной цене.
4. Через год — поздравление с годовщиной и предложение Anniversary Session.

В результате вместо одного заказа клиент мог приобрести три и возвращаться в дальнейшем.

Это пример контекстного follow-up:

`completed Order → future opportunity → reminder`

Система не просто напоминает о продаже, а понимает, **почему и когда возникает следующий логичный контакт**.

---

# 20. STOP

У фотографа может быть минимум один тяжёлый клиент за сезон.

Причины конфликтов могут не зависеть от фотографа:

- нарушение сроков;
- плохой свет;
- погода;
- солнечное время прогулки;
- грязное платье;
- внешний вид клиента;
- костюм жениха;
- ошибки других подрядчиков;
- общая напряжённость свадьбы;
- попытка обмана.

Фотограф часто оказывается последним эшелоном, на которого переносится ответственность за проблемы всего события.

Негативные отзывы могут сильно психологически воздействовать на человека в этой профессии.

Поэтому STOP имеет не только CRM-смысл.

Он позволяет исполнителю **закрыть для себя инициативную часть отношений** и перестать получать автоматические напоминания о клиенте.

---

# 21. Правильная модель STOP

STOP — это не:

- оценка клиента;
- бан;
- «плохой клиент»;
- негативный рейтинг;
- причина для блокировки входящих сообщений.

STOP означает:

> **остановить автоматические исходящие коммуникации с этим клиентом.**

После STOP EventOS прекращает:

- напоминания о годовщине;
- повторные предложения;
- follow-up;
- маркетинговые напоминания;
- другие инициативные контакты.

Но:

- история сохраняется;
- клиент может обратиться сам;
- новый Order можно создать вручную;
- STOP можно снять вручную.

Главное правило:

> **STOP запрещает EventOS инициировать отношения, но не запрещает клиенту возобновить их.**

---

# 22. Почему STOP не должен быть автоматическим

Один и тот же клиент может:

- негативно высказываться в личной переписке;
- публично хвалить фотографа;
- выкладывать его фотографии;
- рекомендовать его;
- снова обращаться спустя годы.

Например, клиент мог лично предъявлять претензии, а публично выложить свадебные фотографии с восторженной подписью и назвать фотографа лучшим фотографом города.

Поэтому EventOS не должен автоматически определять состояние отношений по:

- отзывам;
- переписке;
- количеству заказов;
- публичной похвале;
- рейтингу.

STOP — это **ручное решение исполнителя**.

---

# 23. STOP и повторное обращение

Если клиент с активным STOP снова приходит сам, система должна показать состояние, но не мешать человеку принять решение.

Возможные действия:

- оставить STOP;
- снять STOP;
- создать новый Order вручную.

Таким образом, STOP является настройкой **инициативы системы**, а не запретом человеку.

---

# 24. Главный архитектурный вывод

EventOS постепенно проявляется как система, в которой:

```text
User ID
    ↓
Event / Order / другие сущности
    ↓
связи через ID
    ↓
специализированные Plans
    ↓
коннекторы
    ↓
разные представления одного общего графа
```

Сложность разных веток различна:

| Ветка | Основная сложность |
|---|---|
| LightPlan | 4 временных слоя + погода + свет |
| BakerPlan | составной заказ + техкарты + производство |
| FloristPlan | близкая к BakerPlan модель |
| MakeupPlan | минимальная адаптация фотографической модели |
| Ведущий | урезанная фотографическая модель |
| Driver PWA | минимальный Micro Plan |
| Organizer / EventPlan | объединение множества исполнителей и их Plan'ов |

Поэтому EventOS не должен заставлять каждую профессию становиться отдельным приложением.

Главная модель:

> **ядро объектов и ID + специализированные представления + подключаемые коннекторы.**

А сам Core может быть не спроектирован заранее, а **выделен из устойчивого пересечения всех работающих веток**.
